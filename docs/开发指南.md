# 开发指南

这份文档给后续改 `codex-switch` 的人用。它记录当前 `master`（`fe14af0`，版本 `20261001.5.0`）的模块边界、不变量和改动入口。

用户可见行为的完整说明仍在 `docs/wiki/`。那些英文页面由 CI 发布到 GitHub Wiki，改行为时要同步改对应页面，不要只改已发布的 Wiki。本文不重复命令手册，只回答「改哪、不能破什么、怎么验证」。

本仓库是 [xjoker/codex-switch](https://github.com/xjoker/codex-switch) 的 fork（`Listen3/codex-switch`）。上游约定：代码注释、提交说明和仓库内技术说明用英文；面向用户的中文只放在 `README_CN.md` 和 `docs/wiki/Chinese-Guide.md`。本指南是给本 fork 后续开发用的中文地图，不替代那两份用户文档。

## 这个程序做什么

单个 Rust 二进制。它在**下一次 Codex 会话开始之前**管理本机登录、查看额度、选出账号，或用自定义 API 启动 Codex。

它不做这些事：

- 没有常驻 daemon、PID 文件、内部定时器或服务管理器。旧 daemon 只剩 `src/legacy_daemon.rs`：被旧 LaunchAgent / systemd / 计划任务拉起时，卸掉旧注册然后退出。
- 不在进行中的会话里热替换账号。`use` 只改 `$CODEX_HOME/auth.json`；Codex 0.157+ 的交互会话挂在 app-server daemon 上，daemon 启动时读一次认证。所以凭据真的变了、且 daemon 正在跑时，才调用 `codex app-server daemon restart`（每次调用最多 15 秒）。重启会打断挂在上面的回合。`[use] restart_app_server = false` 可以关掉。
- 不代理 Codex 的 WebSocket，也不在额度用尽时把另一个账号注进正在跑的进程。那是另一个同名项目的模型，不要往这个仓库里加。
- 不在 crates.io 发布。`cargo install codex-switch` 会装到无关的包。分发只走 GitHub Releases 的安装脚本。

支持基线是 Codex CLI `0.159.2`。`launch` 在选号、消耗重置卡、创建 provider run、写入凭据之前，先对 PATH 上解析到的那一个可执行文件做版本探测（最多 4 秒，临时 `CODEX_HOME`）。低于基线、读不到版本或探测失败都直接拒绝。

ChatGPT 文件登录要求 `$CODEX_HOME/config.toml` 里有 `cli_auth_credentials_store = "file"`。受管配置若 `forced_login_method = "api"` 则不兼容。存在 `OPENAI_FEDERATION_RULE_ID` 或 `OPENAI_IDENTITY_TOKEN_FILE` 时，文件登录在产生副作用之前拒绝。

## 两条产品线不能混

| | ChatGPT 账号 | 自定义 API 提供方（Beta） |
|---|---|---|
| 磁盘 | `$CODEX_SWITCH_HOME/profiles/<alias>/auth.json` | `$CODEX_SWITCH_HOME/providers/<alias>/provider.toml` 加 `models.json` |
| 活状态 | 写入 `$CODEX_HOME/auth.json` | 不碰 `auth.json` |
| 启动 | `use` / `launch <别名>` / 无别名自动选号 | 只有 `launch <别名>` |
| 额度与评分 | 有 | 没有，也不进自动选号 |
| 密钥 | OAuth refresh / access / id token | bearer key，只注入子进程环境变量，绝不出现在 argv |

`use` 遇到 provider 别名必须失败。无别名的 `launch` 只在参数明确是在恢复某次 provider 会话时才走进 provider 分支，否则仍是 ChatGPT 选号。

`use` 把用户 `config.toml` 顶层和当前 profile 里已有的 `model_provider` 改回 `"openai"`。替换用 TOML span 的字节范围，保留注释、其他 provider 定义和其余字段。项目级 `.codex/config.toml`、`openai_base_url`、`OPENAI_BASE_URL` 和额外 Codex profile 不在切换范围内。

## 进程怎么进来

`src/main.rs` 只调用 `codex_switch::run_cli`。逻辑在 `src/entry.rs`：

1. `extract_launch_passthrough` 把 `launch` 后面要原样交给 Codex 的参数拆出去，避免 clap 吃掉它们。
2. `Commands::Daemon` 在读配置之前就退出，这样坏掉的旧 `config.toml` 也不会挡住旧服务清理。
3. `config::init` 读一次 `$CODEX_SWITCH_HOME/config.toml`。文件缺失用默认值；文件在但读不了或解析失败则立刻失败。
4. 日志：TUI 不往终端画 tracing；JSON 模式的进度走 stderr；`--debug` 覆盖 `RUST_LOG`。目标 `codex_switch::reported_error` 不进 stderr，避免和已经打印的错误重复。文件日志失败只警告，不阻止切号。
5. 非 JSON、且命令不是 login / import / self-update / doctor / open / launch 时，做一次活 `auth.json` 变更检测。非交互终端只提示，不静默改档。
6. `dispatch` 把命令交给 `src/commands/`。命令模块编排；领域模块实现可复用行为。

库目标是 `src/lib.rs`。集成测试需要的模块是 `pub`，只给二进制用的模块允许 `dead_code`，这样公开模块仍有真正的死代码检查。

## 磁盘与锁

默认 `$CODEX_HOME=~/.codex`，`$CODEX_SWITCH_HOME=~/.codex-switch`。后者永远不改变 Codex 读认证的位置。

| 路径 | 谁拥有 |
|---|---|
| `$CODEX_HOME/auth.json` | Codex 正在用的认证。切换和 launch 暂存都会动它 |
| `$CODEX_HOME/config.toml` | Codex 配置。切换时只改已有的 `model_provider` 选择 |
| `profiles/<alias>/auth.json` | 保存的 ChatGPT 凭据 |
| `providers/<alias>/provider.toml` | 端点、模型、bearer key。目录 `0700`，文件 `0600` |
| `current` | 当前别名 |
| `deleted-profiles/` | 可恢复删除。不能删当前正在用的 profile |
| `recovery/` | 导入时身份对不上、不能进可选树的轮换凭据 |
| `cache.json` | 额度、工作区名、被认证服务器永久拒绝的凭据指纹 |
| `config.toml` | 本程序配置 |
| `logs/` | 滚动诊断日志 |
| `auth.lock` | 串行化活 `auth.json` 的替换和同步。等待上限 15 秒 |
| `launch.lock` | 串行化 `launch` 的临时认证暂存 |
| `*.json.bak.<pid>.<unix>` | 单次 launch 的活认证备份，避免并发 launch 互相覆盖 |

凭据和缓存用原子替换。缓存还有进程内互斥锁加跨进程文件锁。Windows 上目录 ACL 已经是当前用户私有时不要重复写，否则切换会变慢。锁文件不要靠删除来「恢复」：另一个进程可能还拿着它。

`CODEX_SWITCH_HOME` 可以整目录搬走。测试凡是会碰到用户状态，必须把 `HOME`、`CODEX_HOME`、`CODEX_SWITCH_HOME` 指到临时目录。

## 凭据不变量

这些规则已经有回归测试。改认证、导入或刷新时先读 `tests/test_refresh_persistence.rs`。

- 身份以 `account_id` 为准。两边都没有 `account_id` 时才用邮箱。一边缺字段不算冲突：旧 token 后来才带上 email 或 account id，仍然视为同一账号。导入和重新登录用更严的匹配；刷新用 `identities_compatible`，不要把这两套规则并成一个。
- 导入是只创建。Usage API 能证明工作区成员身份，但一个 Team 工作区 ID 可以属于多个人，不能据此覆盖已有 profile。
- refresh token 一经认证服务器轮换，旧 token 就作废。新凭据必须先按 compare-and-swap 写回 profile：呈交上去的 refresh token 还在文件里才写入。并发重新登录赢了这场 CAS 时，这次响应不能再拿去发请求，也不能写入缓存。字节级相同的重复写入算成功。写不进去是失败，不是警告；不能为了「完成额度查询」再拿新 refresh token 打第二次。
- 终端拒绝（`refresh_token_reused`、`refresh_token_invalidated`）记在缓存里，指纹是凭据本身。凭据没换之前，普通刷新和无人值守刷新不再呈交它。只有 `--force` / `list -f` 会再次呈交。签入新登录会清掉这条记录。
- 策略检查在发一次性 refresh、写活认证、发后端请求之前做。已经发下来的替换 token 仍要先落到保存的 profile；策略拒绝只跳过激活，不丢掉这份凭据。
- 活认证是否变化用规范化 JSON 比较。只改格式、或选中已经在用的同一份凭据，不重启 daemon。
- 切换中途失败要回滚 `auth.json`、`current` 和改过的 `config.toml`。Windows 上原子替换成功后 ACL 加固仍可能失败，回滚必须覆盖这种情况。
- 日志、JSON、提交和文档里不能出现 token、`auth.json`、邮箱、account id、工作区名、provider key 或代理口令。`src/usage/api.rs` 的诊断别名和错误码路径已经刻意丢掉不可信的认证响应正文。

## 选号

`score_unified` 在 `src/usage/scoring.rs`，无 I/O。CLI `use` 和 TUI 走 `score_candidates`。Usage API 的 `plan_type` 优先于 JWT。

先淘汰，再打分。淘汰条件：

1. 5 小时和 7 天窗口都没有权威数据。
2. 任一窗口已用满，且还没过重置时间。过了重置时间的用量按 0 计。
3. 7 天剩余低于 `safety_margin_7d * 0.25`（至少 1 个百分点）且离重置超过 48 小时。默认 `safety_margin_7d` 是 20。
4. Free 计划有 5 小时数据时，剩余低于 `FREE_FLOOR_PCT`（35）淘汰。

分数是五项之和：

| 项 | 范围 | 含义 |
|---|---|---|
| `tier_bonus` | 0 或 500 | `team_priority` 打开时 Team 计划加 500 |
| `headroom` | 0..1100 | 用当前消耗速度估计 5 小时窗口还能撑多久。没有 5 小时数据给 50。已耗尽的号最高 500，只用于「没有合格号」时的回退排序 |
| `sustain` | -800..0 | 7 天额度分到剩余每个 5 小时窗口还够不够。48 小时内重置会减轻惩罚 |
| `drain_value` | 0..300，再乘权重 | 5 小时窗口 60 分钟内重置且还有剩余时，鼓励用掉即将作废的额度。池子不超过 2 个时权重 0.5；大部分号已耗尽时 0.3；至少 5 个号且耗尽比例低于 0.3 时 1.5 |
| `recency` | -60..0 | 刚用过的号略降权 |

没有合格号时仍按分数排序不合格候选，调用方自己决定是否提示重置卡。交互式 `use` / `launch` 可以问；JSON 和非终端必须显式 `--consume-card`，默认拒绝。

`account_limited` 把两个窗口都视为用满。

## 启动

`launch_interactive` 的顺序是固定的，不要为了少一次进程探测而调换：

1. 解析 PATH 上的 Codex，并做最低版本检查。失败则还没有选号、没有消耗重置卡、没有创建 provider run。
2. 别名是 provider，或无别名但参数在恢复 provider 会话：走 `launch_provider`。不调用 `ensure_file_credentials_store`，不暂存 `auth.json`。每次启动在共享的 `CODEX_HOME` 里选一个 `cs-*.config.toml` 原生 profile，运行时 provider id 各不相同。MCP、skills、plugins、hooks、会话留在用户的 Codex home。key 进子进程环境变量 `env_key`。
3. 其余情况才检查 file credential store，再选 ChatGPT 号。
4. ChatGPT 参数若还没指定 server / remote / agents，则在 Codex `--help` 列出 `--no-daemon` 时自动加上。这次探测最多 10 秒。探测失败就在写入凭据之前拒绝，因为无法确定会话会不会被 daemon 吃掉、从而读到别的账号。
5. 把目标 `auth.json` 暂存到活文件，等 Codex 读完（默认 `launch.restore_delay_secs`，最小有效值 3 秒），再恢复用户原来的活认证。0 会让会话跑在错误账号上且没有报错，配置层已经拒绝 0。
6. 从暂存开始就要接住 SIGINT / SIGTERM，退出路径必须恢复备份。若 Codex 在暂存期间刷新了 token，且刷新后的活文件仍属于这个别名，把更新写回该 profile，不要用旧备份盖掉。

Provider 的 Responses 探测结论保存 7 天，作用域是模型、key 和连接指纹（端点、头、query、目录）。`launch` 平时不再请求网关。只有保存的结论是「不支持」时才现场再探一次：仍然不支持才拒绝；支持则更新记录；网络失败或不确定则警告并丢掉记录，然后继续启动。

清理旧的 provider run 时，读不了、被截断、过大或格式不明的 rollout 视为这次扫描不完整，保留对应恢复 profile。不要为了「目录看起来脏」就删。

## 预热

`warmup` 只为了打开付费账号的 5 小时窗口。只有 7 天窗口的 Free 账号跳过。两个窗口都空的账号仍是目标，因为第一次请求才会让倒计时出现。

模型顺序：账号自己的目录里先 Luna，再 mini，再按 API 优先级。唯一一次 HTTP 400「not supported」重试会排除被拒绝的模型。算成功必须读完流并且看到 `response.completed`。缓存里 0% 已用、但窗口还没真正走过 5 分钟的冷窗口，不能随着缓存变旧被当成「已经预热」。

## TUI

`src/tui/keymap.rs` 的 `KEYMAP` 是快捷键唯一来源，状态栏和帮助都从它渲染。同一动作在各页用同一个键。`o` 是启动，`l` 是重新登录，不要把启动绑到 `l`。

四个页：Accounts、Providers、Settings、Logs。额度、评分、重置卡只在 Accounts。提供方的新增、编辑、重命名、删除只在 Providers。网络和磁盘动作在 `src/tui/app.rs` 里挂起界面后执行，不要写进 `ui.rs` 的绘制函数。

Accounts 上 `u` 切换选中号并在状态行显示进度；`t` 只在本次 TUI 会话里自动刷新；菜单里的 `w` 对选中号做一次预热。没有后台服务。只有 TUI 启动时会自动检查更新，其他命令不会。

## 配置

`$CODEX_SWITCH_HOME/config.toml`，结构在 `src/config.rs` 的 `AppConfig`。

| 键 | 默认 | 注意 |
|---|---|---|
| `proxy.url` / `proxy.no_proxy` | 空 | CLI `--proxy` 和 `CS_PROXY` 优先于文件和环境变量 |
| `cache.ttl` | 300 秒 | `--force` 绕过额度缓存，但不撤销已记录的永久认证拒绝 |
| `network.max_concurrent` | 20 | 0 会被改成 1 |
| `tui.auto_refresh_interval_secs` | 300 | 小于 30 会被抬到 30 |
| `use.safety_margin_7d` | 20 | 评分和淘汰共用 |
| `use.team_priority` | true | |
| `use.restart_app_server` | true | |
| `launch.restore_delay_secs` | 3 | 0 非法 |

`[use].mode` 和 `[use].min_remaining` 是已删除的旧键，加载时警告并忽略。旧 `[daemon]` 字段不再读取，文档里让用户删掉即可，不要重新实现。

代理优先级：`--proxy` > `CS_PROXY` > 配置文件 > `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY`。支持 http、https、socks4、socks5、socks5h。日志里打印代理地址前要去掉用户名和口令（`auth.rs` 里已有 `sanitize_proxy_url`）。

## 自更新与安装

直装位置是契约，不要收成一个跨平台路径：

- Unix 默认 `$HOME/.local/bin`
- Unix `--system` 才是 `/usr/local/bin`
- Windows 是 `%LOCALAPPDATA%\Programs\codex-switch`
- Homebrew 安装仍归 Cellar，不要让 `self-update` 覆盖它

`self-update` 除了 SHA-256，还要用 `gh attestation verify` 把产物钉到本仓库、release workflow 和确切的 tag。安装脚本始终校验校验和；来源证明在安装脚本里是可选的，在 `self-update` 里不是。本地 `cargo build --release` 只用于诊断，不是发布物。

版本号是 `YYYYMMDD.N.0`。发布、打 tag、移动滚动 `dev` tag 由维护者做。`dev` 分支和名为 `dev` 的滚动 tag 不是一回事。正常功能 PR 在上游指向 `dev` 分支；`master` 是稳定发布。

## 测试与提交前检查

```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test --all
cargo audit
bash -n scripts/install.sh
```

Windows 上再解析 `scripts/install.ps1`，不要执行它：

```powershell
$tokens = $null
$errors = $null
[System.Management.Automation.Language.Parser]::ParseFile(
  (Resolve-Path 'scripts/install.ps1'),
  [ref]$tokens,
  [ref]$errors
) | Out-Null
if ($errors.Count -gt 0) { $errors; exit 1 }
```

有可观察行为的改动，先加一个会因预期原因失败的测试，再改实现。纯文档、只改配置默认值、只改 TUI 外观，不必造一个假的红灯测试，但要写明怎么验证。

HTTP 用 `tests/mock/` 和现有 transformer，不要拿真实账号打生产环境。平台相关改动不能用「本地 Windows 过了」代替 Linux 和 macOS 的 CI。

当前对齐记录在 `docs/CODEX-ALIGNMENT.md`：基线 Codex `0.159.2`，稳定版 `v20261001.5.0`。付费账号在生产后端上的真实额度激活、以及企业策略部署，不在已有自动化覆盖里。改 OAuth、用量解析或模型目录时，先对照那份文档列出的 Codex 源文件，不要根据一次抓包把字段写死。

## 改完要一起动的文档

- 用户能看到的命令或行为：`docs/wiki/` 里对应页，快速开始变了再改 `README.md` 和 `README_CN.md`
- 模块边界或数据流：`docs/wiki/Architecture-Overview.md`，以及本文件里失效的段落
- 工程流程：`docs/wiki/Developer-Onboarding.md` 或 `CONTRIBUTING.md`
- 本开发周期的行为变化：`docs/CHANGELOG.md`
- 发布步骤变了：`docs/RELEASE.md`

## 动手前的短检查

1. 这次改动落在 ChatGPT 路径、provider 路径，还是两条都会碰到？
2. 会不会写 `auth.json`、profile、cache 或 provider key？会的话，锁、原子写和回滚在哪？
3. 会不会把密钥、token 或账号标识带进 argv、stdout、日志或错误字符串？
4. JSON 模式的 stdout 是否仍然只有结构化输出？
5. 失败时是否会多打一次已经作废的 refresh token，或在探测失败之后才写凭据？
6. 测试是否使用隔离的 home，而不是当前用户的 `~/.codex`？
